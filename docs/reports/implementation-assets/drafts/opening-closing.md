# 摘要

校园中的餐饮、零售和服务商户每天产生多笔收款与退款。订单状态、渠道交易结果和账单到达时间并不总是一致，跨日退款、通知丢失、重复账单与未知归属记录又使人工核对更加困难。Reconis 将这些问题组织为“交易确认—账单核对—差错处理—独立复核”的连续业务过程，保存资金事实、原始账单和处理依据，使统计结果能够追溯到具体交易。

系统采用 Vue 与 Spring Boot 构建浏览器应用，以 SQL Server 2022 存储关系数据。最终数据库包含15张业务表、207个字段、32个外键、27个检查约束，以及5个存储过程、2个标量函数和9个触发器。收款与退款采用独立资金事实，金额以整数分保存；本地事务、业务唯一键、行版本和持久租约共同处理重复请求与并发状态变化。对账保留原始输入和历史批次，通过标准事件键比较两侧记录；差错处理与客观核对结果分开保存，经办人与复核人相互独立。系统还实现中文全文检索、历史批次比较、案例推荐、逐级钻取、关联统计及多格式数据交换。

2026年11月4日对当前实现重新验证：前端5项测试、后端190项测试（含72项数据库集成测试）、26组HTTP业务验证和11项浏览器验收全部通过，后端无跳过项。独立数据库中完成1万和10万条流水规模实验。教学环境中的完整业务过程已验证；支付宝沙箱收款与退款采用2026年10月22日可追溯的历史联调记录，真实公网通知和真实业务日账单自动核对仍未验证。实践表明，业务标识、统计时间口径和异常状态的明确建模，比单纯增加界面功能更能保证系统结果可解释、可复查。

关键词：校园支付；SQL Server；对账；事务一致性；差错协作；数据钻取

# 目录

# 1 项目背景与最终范围

## 1.1 业务问题与建设目标

校园咖啡店、文印店和便利店具有交易频繁、单笔金额较小、门店分散的特点。商户需要知道今天实际收到了多少款、哪些退款已经退回、渠道账单与本地记录是否一致。平台财务需要跨商户识别未归属交易和差错，处理人员则需要知道差错由谁负责、依据是什么、何时可以结案。只维护一张“订单是否支付”的表，无法同时回答这些问题。

典型困难包含三类。第一类是结果到达不同步：用户已在渠道付款，通知却尚未到达，本地不能把超时直接等同失败。第二类是业务日期不同步：前一天的收款可能在次日退款，把退款倒扣回原订单日期会扭曲每日净收款。第三类是证据不同步：后续取得的修订账单可能证明差异已经消除，但早先对账结果和人员处理记录仍需保留。系统的目标因此不是简单汇总订单金额，而是建立可确认、可核对、可追溯的资金记录。

最终选题为“校园多商户跨日支付对账与差错协同处理系统的设计与实现”。主要目标包括：按角色管理商户、门店与订单；确认收退款并避免重复记账；导入和核对渠道记录；将差错分派给人员并独立复核；在统一统计口径下提供图表、钻取、关联查询及导出。公开产品首页用于介绍已有能力，实际业务在登录后的工作空间完成。

## 1.2 参与主体与业务边界

系统中的商户是业务数据隔离主体，门店属于商户，用户通过商户成员关系获得工作权限。消费者查看本人订单并提出退款申请；收银人员办理订单；商户财务处理账单和退款；复核人员检查工单结论；平台财务处理跨商户及未知归属事项；管理员维护账号与资料审核；审计员查看记录。平台角色与商户内角色共同决定权限，第8章给出操作边界。

本系统是可在本地浏览器使用的校园支付业务管理应用，不是替代 SQL Server 的通用数据库管理工具。发布包同时提供网页与接口，数据库和文件目录构成持久化部分。本机运行不需要公网服务器；真实支付宝异步通知需要另行配置公网 HTTPS 入口。

系统不包含储值钱包、充值、提现、银行清算、真实商户进件或资金托管。DEMO 环境模拟渠道结果，ALIPAY_SANDBOX 环境调用支付宝测试接口，两者使用不同数据库及文件根目录。报告中的测试交易均为教学或沙箱数据，不能解释为生产经营流水。

## 1.3 成果及验证范围

最终成果包括前后端源程序、数据库建表与升级脚本、可执行发布包、测试脚本及本报告。当前运行版本为 homepage-redesign-20261104-r1。2026年11月4日的数据库实物、测试日志和页面截图共同说明该版本的实现情况；较早的沙箱记录在测试章单独标明日期，避免把历史结果当作本轮验证。

# 2 需求落实与功能结构

## 2.1 功能组织

功能按身份与基础资料、收退款、账单核对、差错协作、经营分析、知识与审计六组组织。图2-1展示用户能够完成的操作，而不是技术框架之间的调用关系。基础资料支撑交易发生，资金事实成为对账输入，非匹配结果形成工单，处理结论与客观结果共同进入分析和审计。业务主线既可以从一笔订单进入，也可以从一条账单差异反向追溯。

![图2-1 Reconis 最终功能结构](implementation-assets/function-map.png)

数据管理保留必要的新增、修改和删除能力，同时服从资金记录的业务约束。例如草稿订单可以修改和删除，已发生收退款的事实则不可通过普通删除入口抹去。商户和门店的状态控制后续可用性，不以删除历史交易来停用主体。这样的边界使管理功能完整，又不破坏历史查询。

## 3.2 模块化单体与数据流

图3-1展示最终技术结构。浏览器以同源 /api/v1 请求后端；Spring Boot内部按身份、交易、支付、对账、工单和分析划分模块，MyBatis执行参数化SQL和数据库程序。它是模块化单体，没有独立微服务、消息队列、Redis或专用OLAP服务。

![图3-1 系统架构及数据流](implementation-assets/architecture.png)

支付适配层选择DEMO或支付宝沙箱。可信渠道结果进入确认过程后才形成资金事实；账单下载与人工上传都经过解析校验再成为对账输入。文件保存原件和证据，数据库保存文件标识、散列与业务关联。统计从事实与结果中读取，生成图表与报表，不反向修改交易。

定时恢复任务与Web服务在同一进程运行，但任务状态和租约保存在数据库。服务短暂中断后，可以依据已保存状态查询渠道和继续处理。外部网络调用放在数据库事务外；数据库事务保证本地写入的一致性，不能被描述为跨支付宝和本地库的原子分布式事务。

## 3.3 本地部署与环境隔离

开发时Vite可代理后端接口，发布时前端静态产物进入后端可执行包，因此浏览器只需访问 http://localhost:8080。公开页为 /welcome，登录页为 /login，认证后 / 为工作台。已登录用户可以直接进入业务路由，无需重复经过展示页。

DEMO使用ReconisDemo及demo文件目录；ALIPAY_SANDBOX使用ReconisSandbox及sandbox目录。启动检查要求环境、数据库和文件目录组合一致，避免把测试渠道请求写入另一环境。数据库连接池最大5、最小空闲1，单文件上传上限20MB，会话空闲超时60分钟。这些是本地配置，不代表并发承载指标。

本机使用HTTP，数据库连接加密但信任本地证书。正式公网部署需要配置HTTPS、可信证书、密钥管理、备份恢复及运维监控。报告不包含账户密码、应用私钥或私有配置值，复现命令通过既有本地配置读取连接参数。

# 10 设计调整与实践总结

## 10.1 从初期方案到最终实现

初期方案已确定Java、Vue和SQL Server的技术方向，也规划了15张表、跨日收退款、对账协作、全文检索和统计钻取。最终实现的主要变化是把这些功能细化为可执行的约束、持久状态与验证方法，而不是更换技术名称。初期系统设计报告作为开发前成果独立保留，最终总结记录实现中的调整及其理由。

表10-1 主要设计细化及原因

| 初期关注点 | 最终落实 | 调整原因 |
| --- | --- | --- |
| 重复请求不重复入账 | UUID、稳定渠道业务号、资金源唯一键、短事务锁、租约与令牌 | 重复点击、并发恢复和迟到响应发生在不同层，单一按钮禁用不能覆盖 |
| 自动获取账单 | 数据库持久任务、限时下载、重试、子批次复用、TEMPLATE_ONLY | 下载成功与业务账单真实有效是两件事，模板不能用于生成交易差错 |
| 多维统计与钻取 | 发生日与记录时点分离、asOf截面、父子范围求交、重跑去重 | 同一金额应在不同粒度下守恒；后到事实不能被伪装为早已获知 |
| 留存处理证据 | 原件散列、审计前后值、独立复核引用、权限内档案导出 | 人工结论需要事实支撑，共享文件不能向单商户泄露其他数据 |
| 差错闭环 | 原始差异、最新结果与人工结案状态分别保存 | 工单关闭不能改写当时观察到的差异 |
| 业务界面 | 公开首页、角色工作台、移动布局和统一操作反馈 | 降低入口和日常操作成本，同时保持原有业务路径 |

## 10.2 问题定位、处理与效果

支付预下单超时暴露了“失败”和“尚不知道结果”的区别。如果超时后立即创建新支付号，既无法查询原请求，也可能造成重复收款。最终实现持久保存UNKNOWN和原交易号，再通过主动查询恢复。租约防止多个恢复线程同时派发，随机令牌限制迟到响应的写入资格，终态条件防止成功被覆盖。本轮针对性测试覆盖这些竞争条件，实际DEMO流程也确认主动查询能补全丢失通知。

中文全文检索在首次初始化或内存紧张时出现过长等待。定位时需要分别观察SQL Server全文组件、分词器初始化和应用请求超时，而不能把所有延迟归为页面问题。最终增加异步预热、READY/WARMING/UNAVAILABLE状态和失败后的重试，让检索就绪情况可观察。本轮新写入案例能够被FREETEXTTABLE检索，独立规模实验也记录了耗时；该结果不意味着低内存环境中永远不会超时。

渠道账单联调中，下载的ZIP确实存在且散列一致，但内容是模板。若仅以HTTP成功作为条件继续对账，模板记录会被当成实际收退款。最终在非DEMO自动下载流程中保留原件和解析结果，并以TEMPLATE_ONLY结束，未生成账单行或业务差错。这个处理明确了“采集已完成”和“业务核对可进行”的不同含义。

统计曾面临两个容易隐藏的错误来源：一是钻取到月份后扩大原先只选一周的范围，二是将资金流水直接联接多条工单导致同一金额累计多次。最终通过父子日期交集、共享asOf和分开聚合资金/差错/工单处理。150元收款、30元退款与120元净额在商户、门店和明细层保持一致，比仅检查图表是否显示更有意义。

多人协作中的覆盖问题发生在保存、改派、上传和复核之间。页面读取旧版本后不能无条件UPDATE；最终操作同时检查受派人、状态和ROWVERSION，冲突返回409，失败上传清理新文件。数据库复核过程还检查submitted_by，避免仅比较当前assignee后遗漏改派历史。这些控制把“操作成功”的含义限定为对当前有效版本完成了合法变化。

## 10.3 数据库与工程实践收获

首先，数据模型必须区分对象和事实。订单描述交易意图，支付尝试描述渠道交互，资金流水描述确认结果，账单行描述外部输入，工单描述人员处理。将这些概念合并在单表中虽然少写几次联接，却容易用一个状态覆盖不同时间的事实。分离模型后，跨日退款、第二笔真实收款和历史批次都能够得到正确表达。

其次，范式与一致性需要结合业务讨论。把名称从订单中拆到商户和门店，可避免重复更新；但事件键、原始文件散列和观察时点是为溯源保留的信息，不能仅因可从其他字段推导就随意删除。相反，有意冗余的金额和标识必须有确定的写入入口与校验，不能只在报告中宣称“满足第三范式”。

第三，应用事务与外部调用之间必须有清楚边界。本地事务适合完成额度预留和多表入账；等待支付渠道时持锁会拉长阻塞。将网络交互放到事务外后，就必须接受并正确管理中间状态，通过原请求号、唯一键和查询补偿恢复，而不能许诺不存在中间状态的“绝对一致”。

第四，查询正确性不等同于SQL可执行。对账需要保留单边记录，风险统计需要避免连接倍增，全文检索需要验证权限范围，钻取需要继承父过滤器，报表需要记录截止时点。测试应围绕这些不变量设计数据，而不是让预期结果机械照抄实现。

最后，前后端协作需要统一接口中的金额单位、ID类型、状态码和错误语义。Long以字符串传到浏览器、金额以整数分计算、409代表陈旧版本、503代表检索未就绪，都能减少接口两端的隐含假设。构建快照、测试日志和可复现样本则让出现问题时有共同讨论的依据。

## 11.2 现有限制

当前验证环境为本地教学部署，未完成生产支付接入、多商户真实支付宝入驻、公网HTTPS签名通知联调或真实业务日账单自动核对。历史沙箱收退款能够说明测试渠道适配有效，不能替代生产资质、结算或运营验证。

权限隔离主要由后端范围谓词和逐接口检查实现，数据库未启用SQL Server行级安全策略。部分外模式视图已部署，但不是所有业务入口都直接查询这些视图。复核员的预下单等接口能力仍有进一步收紧空间，不能笼统宣称其所有API绝对只读。

文件安全采用扩展名白名单、随机路径、大小限制、范围校验和SHA256。散列证明留存字节的一致性，不能鉴定业务内容真实，也不等同恶意文件扫描。证据档案存在每类500条、单文件20MB、总归档80MB的上限，缺失或超限由清单说明。

性能实验在单机、有限数据规模和明确采集条件下完成，不是持续高并发压测。10万流水中每商户5万条，对账需约15.6—20.2秒，后续应继续研究索引覆盖、集合运算代价、任务拆分和资源配置。当前也没有多实例故障切换、备份恢复时限或生产可用性指标的验证结论。

## 11.3 后续改进方向

下一阶段可优先补齐真实签名通知和真实业务账单的端到端证据，随后完善复核角色的细粒度接口能力、文件内容鉴别与恶意内容扫描，并在固定数据和资源条件下进行并发及故障注入实验。数据库方面可结合实际执行计划优化大批次核对，增加备份恢复演练；检索方面可针对中文分词与领域词建立人工评估集，评价推荐效果，而不是凭“能返回结果”推断准确率。

系统目前已经形成可操作的教学业务闭环。实践中最重要的结果，是让一次资金变化、一次核对判断和一次人员结论分别有明确来源、状态和证据，使后续改进能够建立在可检验的数据基础上。
