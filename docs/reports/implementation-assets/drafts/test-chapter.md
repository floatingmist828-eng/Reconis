## 9.3 规模实验与查询结果分析

规模实验先生成1万笔流水，再累计至10万笔，两商户各占一半。每档将2%的渠道记录设置为金额不符，分别执行对账、聚合、分页和全文查询，并采集STATISTICS IO/TIME及实际执行计划。1万档每商户发现100条金额差异，10万档每商户发现1000条；独立逐笔计算的收款总额分别为50,005,100分、500,501,000分，与数据库汇总一致。两档全文查询使用的工单数量分别为200、2000。

**表9-4 规模实验耗时（毫秒）**

| 操作 | 1万流水档 | 10万流水档 |
|---|---:|---:|
| 商户1对账 | 2397.977 | 15574.102 |
| 商户2对账 | 2385.127 | 20226.653 |
| 商户1门店聚合 | 233.658 | 843.120 |
| 商户2门店聚合 | 95.818 | 507.310 |
| 商户1分页，跳过100条取20条 | 142.116 | 145.344 |
| 商户2分页，跳过100条取20条 | 81.736 | 16.681 |
| 全文首次查询，最多30条 | 134.226 | 180.994 |
| 同条件重复全文查询 | 28.641 | 115.042 |

表9-4记录从客户端发起执行到读完结果的总耗时，包含实际执行计划和STATISTICS IO/TIME的采集开销。每次对账处理单个商户，10万流水档中每个商户各处理5万笔，耗时约15.6至20.2秒。批量写入和约束检查成本较高，处理时需要向用户呈现任务状态。

实际计划显示，门店聚合使用 `IX_order_store_time`、`IX_payment_order` 等索引，同时包含扫描、连接和聚合。10万档商户1分页虽然只返回20行，对transaction_entry的逻辑读仍达11,370页，说明关联权限过滤及排序具有成本，后续可研究更合适的访问路径或游标分页。全文查询还需关联批次、结果和权限信息，两个规模档位的查询均在超时前完成。

原始读数见 `performance-results.json`，实际计划见 `performance-20261104-180224`。实验采用顺序单次测量，保留数据库原有缓存；表中的“首次”指同条件查询的第一次执行。实验未重复多轮、施加并发压力或进行删除索引的同期对照。结果反映给定环境中的单次处理成本，吞吐率、P95与索引提速倍数尚未测量。
