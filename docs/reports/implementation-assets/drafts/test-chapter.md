## 9.3 规模实验与查询结果分析

规模实验先生成1万笔流水，再累计至10万笔，两商户各占一半。每档将2%的渠道记录设置为金额不符，分别执行对账、聚合、分页和全文查询，并采集STATISTICS IO/TIME及实际执行计划。1万档每商户发现100条金额差异，10万档每商户发现1000条；独立逐笔计算的收款总额分别为50,005,100分、500,501,000分，与数据库汇总一致。全文工单数量分别为200、2000，不能将10万流水规模称为10万全文案例规模。

**表9-4 规模实验耗时（毫秒）**

| 操作 | 1万流水档 | 10万流水档 |
|---|---:|---:|
| 商户1对账 | 2397.977 | 15574.102 |
| 商户2对账 | 2385.127 | 20226.653 |
| 商户1门店聚合 | 233.658 | 843.120 |
| 商户2门店聚合 | 95.818 | 507.310 |
| 商户1分页，跳过100条取20条 | 142.116 | 145.344 |
| 商户2分页，跳过100条取20条 | 81.736 | 16.681 |
| 全文首次查询，最多30条 | 134.226 | 180.994 |
| 同条件重复全文查询 | 28.641 | 115.042 |

表9-4计时从客户端执行至读完结果。每次对账处理单个商户，因此10万档的一行对应5万笔，不能表述为全库10万笔只需15.6秒。批量写入和约束检查仍有明显成本，应向用户呈现任务状态，避免将其理解为即时操作。

实际计划显示，门店聚合使用 `IX_order_store_time`、`IX_payment_order` 等索引，同时包含扫描、连接和聚合。10万档商户1分页虽然只返回20行，对transaction_entry的逻辑读仍达11,370页，说明关联权限过滤及排序具有成本，后续可研究更合适的访问路径或游标分页。全文查询还需关联批次、结果和权限信息；本轮没有出现超时，但有限样本不能证明所有环境下都具有同样时延。

原始读数见 `performance-results.json`，实际计划见 `performance-20261104-180224`。实验为顺序单次测量，没有清空缓存、重复多轮或施加并发压力，“首次”不是冷缓存；未做删除索引的同期对照。因此这些结果用于说明给定环境中的可行性与成本，不据此推导吞吐率、P95或索引提速倍数。

## 9.4 支付渠道证据与验证边界

本轮HTTP及浏览器收退流程均使用DEMO。公网异步通知的签名反例、幂等与并发测试可以验证本地处理逻辑，不能替代真实支付宝回调联通。浏览器支付失败提示采用只读响应注入，仅证明错误说明的页面呈现。

2026年10月22日11:46:40的历史沙箱记录 `alipay-sandbox-verification-20261022.json` 证明：沙箱付款1分、退款1分均成功，两类账务事实各一条，净额与可退金额为0，退款幂等有效，结果通过ACTIVE_QUERY主动查询确认。这是已完成的历史联调，不计入11月4日的新交易或测试数量。该次下载的1017字节ZIP虽通过哈希校验，但仅含模板，账单行与对账结果均为0，不能证明真实业务日账单对账。

本轮任务103也有明确边界：它于11月4日00:09已成功，17:58重复触发复用了原任务。本轮证明了幂等、原件校验和权限隔离，没有新发生一次渠道账单下载。任务领取、失败恢复和租约处理另由实库测试验证。

在以上范围内，各项测试均达到预期。尚未验证的内容包括生产支付、公网异步回调闭环、真实支付宝业务日账单完整对账、多用户长期压力、真实手机及跨浏览器兼容。报告将这些限制与已经通过的功能分开，保留后续验证入口，避免以局部成功替代完整渠道或长期运行结论。
